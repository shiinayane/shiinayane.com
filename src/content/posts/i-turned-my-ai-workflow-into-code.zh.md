在上一篇文章里，我写了构建 BiliKit 时逐渐形成的工作流。这个 Swift 项目在版本 1 之前就超过了 21,000 行。

简短地说：AI 让代码变得廉价，却没有让一致性变得廉价。随着仓库增长，继续写更长的 prompt 不再有用。我需要持久的项目记忆、明确的任务契约、基于风险的 review、纵向切片、复杂度预算，以及绿色测试套件之外的真实证据。

这套工作流有效。

然后，它制造了一个新问题。

有用的部分被困在一个仓库里。有些存在于 BiliKit 的 `AGENTS.md`，有些存在于质量 Gate 文档和脚本里，还有一些只存在于我操作它们时养成的习惯里。开始另一个项目时，我只能从记忆中重建这套流程，或者把 BiliKit 的规则原样复制过去。

两个选择都不对。

从记忆重建会丢掉让工作流真正可靠的细节。复制文件又会保留太多只对 BiliKit 有意义的东西：B 站协议边界、Keychain ownership、媒体重定向策略、弹幕 renderer 风险，以及只属于一个产品的里程碑结构。

我想复用的不是政策本身。

我想复用的是产生政策的方法。

因此，我建立了一个叫作 `codex-engineering-skills` 的新仓库，并开始把工作流变成两个可复用的 Codex Skills：

- `project-governance-bootstrap`：根据一个真实 checkout 推导项目专属治理；
- `apple-dev-loop`：选择并执行足以证明 Apple 平台工程主张的最小证据循环。

这不是一个把 prompt 打包起来的故事。

这是一个关于我试图把工程判断变成代码之后，发生了什么的故事。

## 工作流被写下来，不等于它可以复用

我的第一反应很直接：把 BiliKit 工程指南里有用的部分提取成一个通用模板。

这个方案几乎立刻失败了。

BiliKit 把认证、重定向、本地服务器、播放、并发、renderer 和破坏性迁移归为高风险工作。这些分类对 BiliKit 很合理，因为产品确实存在这些失败模式。把同一张清单复制到一个静态网站，只会制造流程表演。把 BiliKit 的签名 Keychain 验证要求复制进命令行 parser，更是完全没有意义。

反过来的失败更危险。一个处理凭据的小工具可能不到一千行，却仍然需要比大型生成代码库更严格的控制。仓库规模不能代表后果。

这导出了提炼过程中的第一条规则：

> 复用决策过程，不要复用上一次的决策结果。

治理 Skill 不会宣称每个仓库都需要 BiliKit 的规则。它从阅读仓库自己的 instruction、架构决策、manifest、CI、测试、安全文档和发布边界开始。然后，它选择能够覆盖真实失败模式的最低治理 profile：

- **light**：表面小、可逆、只有一条主要验证路径；
- **standard**：多个模块、公共边界、CI、持久化或多层验证；
- **critical**：凭据、授权、破坏性迁移、不可信输入、本地服务器、媒体生命周期、生产基础设施或难以回滚的改变。

输出仍然属于具体项目。可复用的是 Skill 如何到达这个输出。

回头看，这似乎显而易见。可当规则只在一个项目里工作时，它并不明显。本地工作流会逐渐积累假设，直到那些假设变得不可见。提炼迫使每个假设回答一个更困难的问题：

> 这是普遍原则、平台 profile，还是仅仅属于教会我这条原则的那个项目？

大部分工作都花在拆开这三种东西上。

## Skill 是编译器，不是模板

现在，我更愿意把 `project-governance-bootstrap` 看成一个小型编译器，而不是文档生成器。

它的输入是一个仓库：

```text
code + manifests + ADRs + tests + CI + security boundaries + release rules
```

它的输出是一份可执行的项目契约：

```text
事实来源顺序
+ 架构边界
+ 成比例的风险区
+ 验证入口
+ 授权限制
+ 可选 reviewer 角色
```

编译器不会把上一个程序粘贴到一个新文件里。它读取特定输入、应用规则，并产生适合该输入的输出。

因此，这个 Skill 明确拒绝几条很诱人的捷径：

- 不会整份覆盖已有 `AGENTS.md`；
- 不会移植产品名、路径、阈值和风险分类；
- 不会把行数或模型选择当作证据；
- 不会在独立角色没有持续价值时生成自定义 Agent；
- 不会在已有命令足以证明主张时再创建 Gate 脚本；
- 不会把临时里程碑、测试数量、commit ID 或 CI run 写成永久规则。

仓库里的模板只是起草骨架，不是标准政策。所有无关章节都应该被删除。

这很重要，因为模板具有引力。一个章节一旦存在，人类和模型都会倾向于保留它。通用的“Security”标题会诱导通用安全文字，即使仓库没有真正的安全边界。预先写好的红区列表会鼓励按表面相似性分类，而不是按后果分类。

好的生成式治理，不是最完整的文档，而是能够阻止项目最可能出现的昂贵错误的最小文档。

## 我把一套工作流拆成两个 Skills

BiliKit 的工作流混合了两个彼此相关、却并不相同的问题：

1. 这个仓库需要什么？
2. 我如何证明这项 Apple 平台修改真的工作？

因为 BiliKit 是 Apple 平台项目，而且经常同时需要两者，把它们放在一起很有诱惑力。我还是把它们拆开了。

根 README 用一句话描述两者关系：

> Governance Skill 定义仓库需要什么；Apple Development Skill 在具体任务需要时执行 Apple 平台验证。

`project-governance-bootstrap` 拥有政策推导。它可能发现一个 Apple 仓库需要签名 App 证据、UI 验证或性能 recording，但不会携带所有 Xcode 工具的操作说明。

`apple-dev-loop` 拥有执行过程。它知道如何从源码检查走到 SwiftPM、`xcodebuild`、`.xcresult`、Xcode MCP、XCUI、签名 App、Computer Use、Instruments 和 CI，却不会决定产品架构，也不会发明风险政策。

两个 Skill 都不会加载对方，也不要求对方已经安装。

这和我在应用架构中使用的是同一条边界规则：经常一起使用的东西，不会因此自动属于同一个 owner。

独立带来了实际收益。Governance Skill 仍然可以用于 Rust、TypeScript 或文档仓库。Apple Skill 也可以用于一个已经拥有优秀治理、只需要具体验证循环的 Swift 项目。当两者同时适用时，仓库契约说明必须证明什么，Apple Loop 选择合适的证明机制。

组合比包罗万象更有价值。

## 触发边界也是正确性的一部分

普通函数在返回错误结果时很危险。Skill 甚至可以在运行之前就变得危险——只要它在错误任务中被触发。

如果 `apple-dev-loop` 因为问题里出现了 “Swift” 就自动触发，一段只需要源码解释的问题会突然获得 Xcode preflight、scheme discovery 和构建要求。流程在技术上很严谨，在实践中却无法忍受。

因此，它的 description 同时包含正向和负向边界。它适用于需要端到端证据循环的 Swift、SwiftUI、AppKit、UIKit、Xcode、设备、签名、UI 或性能任务；不适用于只解释源码，或不需要 Apple 工具链和运行时验证的狭窄 Package 修改。

Governance Skill 也有同样约束。它适用于新建、审计或升级仓库治理，而不能仅仅因为仓库里碰巧有一份 `AGENTS.md` 就出现。

这改变了我看待 prompt 的方式。在对话里，多一点指导往往显得没有坏处。在可复用 Skill 里，不需要的指导就是行为。它消耗上下文、改变工具选择、制造流程，并可能让 Agent 执行用户从未要求的工作。

Skill 需要接口，而触发描述就是接口的一部分。

## Progressive disclosure 是上下文的依赖管理

可复用工作流的第一版自然想装下所有东西。

那会产生两个巨大的 `SKILL.md`：一个包含全部风险分类、模板、Agent 角色和 Apple 平台例外；另一个包含全部 Xcode、XCTest、签名、Simulator、UI 和 Instruments recipe。

实际设计中，每个 Skill 只有一份简短的操作核心，并且只在任务需要时加载 reference。

Governance Skill 始终知道如何检查仓库和选择 profile。它在定义风险区前阅读通用治理模型，只对 Apple 平台仓库读取 Apple profile，只在独立角色有持续价值时读取 Agent routing 指南。

Apple Skill 始终知道证据阶梯和工具顺序。它只在配置或使用 Xcode MCP 之前读取相关说明，只加载当前验证层级需要的 recipe。

这通常被称为 progressive disclosure。我更愿意把它看作上下文的依赖管理。

上下文有成本。不同内容会竞争注意力，也会让决策偏向描述最具体、最鲜明的机制。把 Instruments 指南加载进一个简单 Package 测试任务，不只是浪费 token；它会让高成本验证路线变得更显眼，因此更可能被采用。

最好的上下文不是全部可能相关的知识，而是当前决策所需的最小依赖集合。

## 证据阶梯变成了可执行流程

`apple-dev-loop` 的概念中心是一条证据阶梯：

1. 静态契约和源码检查；
2. SwiftPM、单元测试和集成测试；
3. 带结构化 `.xcresult` 的 `xcodebuild`；
4. Xcode-aware 诊断和操作；
5. deterministic XCUI smoke test；
6. 签名 App 和真实 UI 操作；
7. 定向 `xctrace` 或 Instruments recording；
8. CI、设备矩阵和独立 review。

指令不是尽可能爬到最高层。

而是在能够证明主张的最低层停下。

这保留了 AI 工作流很容易丢失的两个性质：可复现性和比例性。截图不能替代单元测试。无签名构建成功不能证明 Keychain access。签名启动不能证明内存生命周期。一台机器上的 30 分钟 trace 也不能证明整个支持设备矩阵。

每一层回答不同的问题。

Skill 在这个模型周围加入了一些小脚本。Preflight 会在昂贵工作开始前记录仓库、project 或 workspace、scheme、选中的 Xcode、developer directory 和相关能力。`.xcresult` summarizer 读取结构化测试结果，而不是要求模型从几千行 console 文本中推测事实。

这些脚本不会自动化所有 Apple 工作流。那只会在 shell 里重新实现一个更差的 Xcode。它们只自动化那些能够通过稳定、有限的事实消除昂贵歧义的部分。

其他工作仍然被路由给拥有它的工具：

- 仓库搜索和 CLI 负责可复现的源码、构建和测试事实；
- Xcode MCP 负责实时 project semantics；
- XCUI 负责稳定用户路径；
- Computer Use 只处理没有更好接口的真实视觉或权限状态；
- `xctrace` 负责具体性能问题；
- 密码、Keychain 解锁、意外权限和不可逆授权仍然交给用户。

工作流变成了代码，却没有假装每一种判断都能被自动化。

## Skills 也需要安全边界

一旦工作流能够采取行动，安装和环境行为就会成为它的安全模型。

仓库里有一个链接脚本，通过一份 canonical editable copy 让每个 Skill 可以被发现。它创建 symlink，而不是复制目录。如果目标已经是完全正确的链接，就保持不动；如果目标是另一个链接或真实目录，就拒绝替换。

这个拒绝看起来很小，却是重要的设计选择。

一个会静默替换现有 Skill 的“安装”工具，会把方便变成数据丢失。为了让一次构建成功就修改全局 `xcode-select` 的脚本，会通过改变机器上所有其他 Xcode 工作流来修复当前任务。未经明确同意就接受永久 external-agent permission 的工具，会把临时访问变成环境权力。

因此，Skills 更偏好注入式局部配置，而不是隐藏的全局变更。它们在歧义时停止，区分“缺少可选能力”和真正 blocker，并且只在操作实际越过授权边界时询问用户。

这和工作流施加在产品代码上的原则完全相同：

- 一个 canonical owner；
- 明确的状态变化；
- 狭窄权限；
- 可逆操作；
- 所需路径被跳过时绝不宣称成功。

可复用工程工作流应该遵守自己推荐的治理。

## 编写 Skill 暴露了我推理里的漏洞

最有价值的结果不是可复用文件，而是形式化带来的压力。

在一个项目里，“对重要工作使用独立 review”听起来足够清楚。进入 Skill 后，它立刻产生一系列问题：

- 什么叫重要？
- 每个跨文件修改都需要 reviewer 吗？
- Reviewer 可以接收哪些信息，才能不继承实现者偏见？
- Reviewer 意见冲突时怎么办？
- 什么时候另一轮 review 有用，什么时候只是流程膨胀？

提炼后的版本变得更窄。绿区不机械获得审查仪式。非机械的黄区工作才接受独立只读 review。红区增加对失败、取消、所有权、安全、清理和回滚的审查，同时也必须有复杂度预算，防止严谨度无限扩张。

证据也发生了同样变化。“运行完整验证套件”变成“如果最高适用 deterministic mode 已经包含低层，就只运行一次”。“在真实设备上测试”变成“只对 deterministic layer 无法证明的主张使用真实环境”。“使用 Xcode MCP”变成“先确认目标 Xcode process、window、workspace、scheme 和当前 tool schema”。

把文字变成操作接口，会迫使模糊经验获得停止条件。

这就是为什么我称它为“把工作流变成代码”。结果主要由 Markdown 和 shell 组成，但它像软件一样行为。它有输入、触发条件、依赖、副作用、失败模式，以及允许做出的主张。

## 指导代码的代码也需要测试

Skills 仓库有自己的 validator。

它检查 metadata、内部链接、未解决 placeholder、shell syntax 和 whitespace，并可选择调用官方 Skill validator。安装使用另一份脚本，具有明确冲突行为。仓库自己的 `AGENTS.md` 把 trigger semantics、模板、脚本、discovery link 和 validation 修改视为真正的工程变化，而不是“只是文档”。

但这些仍然只是结构验证。

一个 Skill 可以拥有完美 frontmatter、有效链接和干净 shell syntax，同时做出糟糕判断。它可能触发得太宽，生成不成比例的治理，遗漏已有项目规则，或者推荐根本不能回答任务的证据。

真正的测试，是从全新上下文 forward use。

对 `project-governance-bootstrap` 来说，这意味着给它不同形状的原始仓库——一个小型可逆工具、一个普通多模块应用、一个真正有安全或生命周期风险的项目——然后检查它是否能产生不同且成比例的契约，同时不泄露 BiliKit 特定政策。

对 `apple-dev-loop` 来说，这意味着给它不同证据层级的具体 Apple 任务，并检查它是否正确停止：Package 主张停在 Package 测试，project 主张走到 `xcodebuild`，Keychain 主张走到签名执行，真正性能问题才进入 Instruments。

Skills 不会因为完成了提炼就自动成熟。写下这篇文章时，仓库仍然很新，这套抽象还没有积累跨项目证据。

这个限制应该属于设计，而不是脚注。

## 仍然属于人的部分

提炼最终自动化的内容，比我最初预想的更少。

它可以检查仓库、生成有限 inventory、路由 reference、验证文件、选择证据层、preflight Apple 环境并总结结构化结果。

它不能决定我应该构建什么产品，不能替我授权高风险实验，不能把猜测阈值变成 requirement，不能知道一个技术完整的功能在战略上毫无必要，也不能判断另一个机制究竟是有用的严谨，还是伪装成工程的恐惧。

上一篇文章最终把人定义为范围、风险和事实的 owner。Skills 保留了这条边界。

它们不编码答案，而是让一些问题更难被跳过。

这可能是我现在能够构建的最有用 AI 工具：不是一个试图取代判断的系统，而是一个承载判断周围繁琐结构的系统——阅读正确事实来源、区分计划和证据、让授权可见、选择最低充分工具，并拒绝把没有证明的主张称为完成。

## 从私人习惯到可测试接口

BiliKit 迫使我停止把 AI 对话当作工程事实所在的位置。

Skills 项目是下一步。它让我不再把个人记忆当作工作流所在的位置。

现在的演进路径是：

```text
个人习惯
    ↓
项目专属规则
    ↓
可复用决策过程
    ↓
独立触发的 Skills
    ↓
面对新项目的 forward test
```

每一步都移除了一种隐藏状态。

项目专属规则让 BiliKit 能够跨对话恢复。Skills 让方法能够跨仓库恢复。Forward testing 将决定这个抽象是否真实，还是我只是为一个项目建立了一份优雅描述。

工作目前就停在这里。

我把自己的 AI 工作流变成了代码。代码能够通过结构验证，边界已经明确，两个 Skills 可以组合，又不互相依赖。

现在，它们必须面对那些没有教会我如何编写它们的项目。
