BiliKit 还没有到版本 1。

这是我用 Swift 6、SwiftUI 和 AVFoundation 开发的一款原生 macOS B 站客户端。写下这篇文章时，仓库里有 125 个 Swift 文件、21,300 行 Swift：大约 12,700 行生产代码和 8,400 行测试。它已经可以浏览和搜索视频、通过 Web 二维码登录、用 AVPlayer 播放 DASH 视频、显示字幕、按照播放时间轴调度弹幕，并在持续负载下完成渲染。

但它仍然没有完成。

UI 还需要一次真正的精修。Mac 特有的产品工作仍在后面。签名、公证、发布工程，以及最终的 V1 回归矩阵，也都还没有结束。

这是我至今做过的、由 AI 真正承担了相当一部分实现工作的最大项目。它也是第一个彻底击穿我原有 AI 工作流的项目。

最初，我的做法和大多数人描述的 AI 编程差不多：解释一个功能，让模型阅读仓库，让它实现改动，运行测试，再修复失败项。对于小型代码库，这种方法有一种惊人的生产力。一个完整功能可以在一个下午出现。模型记得整段对话，diff 也还小到足以逐行阅读。架构稍微弯了一点，也可以很快掰回来。

然后，仓库开始长大。

模型仍然可以快速生成代码。问题不在这里。问题是，每一行新代码都会进入一个系统，而这个系统的不变量已经无法装进一段对话、一个 diff，甚至一个人的短期记忆里。一个局部看来完全合理的修改，可能破坏三个模块之外的依赖边界。一项通过的测试可能掩盖取消竞态。一个性能实验可能悄悄变成生产架构。一个 reviewer 可以提出五项分别看来合理的防护，而它们加起来的成本已经超过了被保护的功能。

AI 越强，我的工作流就越不能依靠“让它表现得更聪明”。

我必须用一个可信的系统，替代对一段对话的信任。

## 第一种工作流：提出要求、检查结果、修复问题

早期的循环很简单：

1. 描述下一个功能。
2. 让 AI 检查相关文件。
3. 要求它实现功能。
4. 运行测试。
5. 阅读 diff，修复明显问题。

对于小项目，这并不是糟糕的工作流。它快速、直接，而且往往已经足够。任务和仓库都还小到让模型可以一次性掌握大部分重要上下文。

BiliKit 比我预期更早地不再是这种项目。

仅仅是播放，就跨越了网络、HTTP Range、SIDX 解析、HLS 播放列表生成、本地 loopback HTTP server、AVPlayer 生命周期、取消、seek 和 CDN fallback。认证跨越远端状态机、ephemeral URLSession、重定向策略、Keychain 存储、请求授权、登出清理和 UI 状态。弹幕则跨越 protobuf 解码、分段预取、去重、统一媒体时间轴、轨道分配、Core Animation、对象生命周期和持续负载行为。

这些并不是互相独立的功能。它们触碰的是同一张状态和资源关系图上的不同部分。

失败很少表现为“AI 写出了无法编译的 Swift”。现代模型很擅长生成合法的 Swift。真正危险的错误通常体面得多：

- 一个类型被放进了最方便的模块，而不是拥有其语义的模块；
- 一项测试之所以通过，只是因为那一次一个 `Task.yield()` 恰好够用；
- 取消路径停止了 UI 更新，却没有释放底层资源；
- 匿名媒体请求意外继承了认证 header；
- benchmark harness 在回答任何产品问题之前，就长成了一个小型框架；
- 文档把预期能力写成了当前已经存在的行为。

这些问题中的每一个，都可能通过一次快速 review。其中一些甚至能通过完整测试套件。

我最初的应对方式是写更长的 prompt。它短期有用，随后却让问题变得更糟。更长的 prompt 仍然只是临时状态。它把产品意图、架构、历史决策、实现细节和今天的任务混进同一个大文本块，内部优先级并不清晰。更多上下文不等于更好的控制。

项目需要一种存在于对话之外的记忆。

## 仓库成为事实来源

第一次真正的改变，是把仓库文档当作可执行的项目记忆，而不是代码完成后补写的说明。

BiliKit 现在有一份区分当前事实和未来计划的 roadmap；有记录那些不应被随手推翻的决策的 Architecture Decision Records；有覆盖认证和个人观看数据的 threat model；有记录环境相关结论的 validation record；还有一份告诉人类和 Agent 各类代码应该归属何处的工程指南。

它们的顺序很重要。

当前代码和构建配置高于一切。已经接受的架构决策排在之后。Roadmap 描述方向和 Gate，但计划不能证明功能已经工作。带日期的验证记录保存某个环境下观察到的事实，而不会假装结果永远有效。

这套层级解决了一个很微妙的问题：AI 非常愿意通过流畅的文字来“消除”矛盾。如果旧验证记录与当前实现不同，最诱人的做法就是让“文档保持一致”。但历史证据不应该被重写来迎合现在。正确做法是识别每种事实由哪个来源负责。

范围也是一样。BiliKit 的 V1 明确排除了下载、转码、直播、多账号、区域解锁和一长串很有诱惑力的支线。AI Agent 可以为其中任何一项生成看起来很有说服力的实施计划。这并不会让它成为产品的一部分。

当生成变得廉价，拒绝也会成为一种工程工具。

## 我不再分派功能，而是定义契约

下一项改变形式很小，影响却很大。任何非平凡任务开始实现之前，现在都要有四个字段：

- **Goal：**唯一需要改变的可观察行为。
- **Context：**相关入口、决策、历史证据和已知限制。
- **Constraints：**依赖方向、安全、取消、生命周期、兼容性和范围边界。
- **Done when：**能够证明任务完成的测试、探针、测量或用户可见行为。

这并不是一份详细实现计划。它的价值恰恰来自拒绝过早变成实现计划。

如果我不能用一句话描述 Goal，这个任务可能夹带了两个可以独立完成的改变。如果 Done when 里只有“测试通过”，我可能还没有识别真正危险的行为。如果 Constraints 变成一整页推测性的防护，我可能是在设计框架，而不是解决任务。

契约改变了我和模型之间的关系。我不再问：“你能实现弹幕渲染吗？”我会给出一个边界清楚的结果、明确的 owner 和停止点。AI 可以在这个盒子里自由推理实现，但不能悄悄重新定义盒子。

它也让上下文变得可以丢弃。一个新对话不需要继承上一个对话的全部推理历史，只需要读取契约、相关仓库事实和待审文件。因为对话连续性看起来像记忆，但它也是偏见。一个参与发明方案的模型，自然更倾向于替方案辩护。

## 纵向工作，而不是逐层铺开

AI 会让横向建设变得格外诱人。

你很容易要求它先写完所有 Domain Model，再写所有 Repository，再写所有 Use Case，最后写所有 View。结果看起来很有架构感，却会产生没有真实调用方的抽象、建立在想象未来上的协议，以及从未参与过一次完整行为的大块代码。

BiliKit 改用了纵向切片。

一个切片从最小的 Domain 或 Application 契约开始，加入具体 Adapter，连接一份 Feature 状态，在 composition root 完成组装，然后证明整条路径。认证不是“建立一个认证框架”，而是 QR 状态、安全凭据所有权、一个受权 endpoint、一条 UI 流程、重启恢复和登出。弹幕也不是“建立一个 renderer”，而是从唯一媒体时间轴、一个分段契约、有界调度开始，最后连接真实 renderer。

架构仍然是分层的：

```text
Scene → View → ViewModel → Use Case → Repository Port → Adapter
```

但实现是在层与层之间纵向移动，而不是沿着一层横向铺开。

这在 AI 时代比以前更重要。模型可以用惊人的速度，在空架构里填满内部一致的代码。纵向切片迫使每个抽象通过一个真实调用方和一个真实可观察结果来证明自己的存在。

没有空 target。没有占位 Repository。也没有等着变成垃圾场的 `Common`、`Shared` 或 `Utils`。

## 决定流程的是风险，不是 diff 大小

我早期的另一个错误，是把小 diff 当作安全 diff。

修改五行重定向处理就可能泄露凭据。修改十行 Task ownership 就可能制造泄漏或旧结果竞态。一次很小的持久化迁移就可能销毁数据。与此同时，一个巨大的自动生成 protobuf 文件可能机械得毫无风险。

因此项目现在按照失败模式分类工作。

绿区包括局部展示改动和狭窄的机械修改。黄区包括普通 Feature、Use Case、跨文件重构和公共 API。红区包括认证、Keychain、媒体、重定向、本地服务器、并发、资源生命周期、renderer、迁移、删除和不可逆操作。

类别会改变过程：

- 绿区运行基线检查，并做聚焦的 diff review。
- 黄区需要明确契约和独立的只读 review。
- 红区需要决策 Gate、复杂度预算、必要时的隔离实验、独立技术审查、真实测量，以及高风险路线进入生产之前的明确用户决定。

把它写成列表时，听起来可能很官僚。实际效果却是从普通工作中移除了官僚主义。并非每个任务都需要全部仪式。分类的目的，是把注意力花在失败昂贵的地方，而不是给所有工作套同一张巨大 checklist。

它也防止一种常见 AI 失败：只考虑提高严谨度，不考虑成本。Reviewer 永远可以再想出一个矩阵维度、一份 fixture、一个抽象、一个对抗案例。“更全面”没有自然停止条件。

对于不确定任务，我现在会在实现前设置复杂度预算：最多允许少量候选、指标、负载等级、可执行程序、fixture 和输出格式。如果 Agent 想超过预算，它必须解释额外机制保护的是哪个决策，以及为什么更便宜的观察无法回答问题。

没有预算的严谨，会成为另一种 scope creep。

## 独立上下文比再检查一遍更有价值

过去我会让同一个对话实现功能，然后 review 自己的工作。这能够发现语法错误和明显遗漏，却不能产生独立性。

实现上下文脑中已经有一套故事：为什么类型存在，为什么妥协合理，为什么测试足够。当它 review 结果时，它会通过这套故事看代码。

对于有意义的修改，BiliKit 现在使用一个全新的只读上下文。Reviewer 得到任务契约、相关事实和修改文件，但得不到实现者的结论。

高风险工作还会进一步拆分问题：

1. **价值与简化：**这项工作真的有必要吗？这是得到有用结论的最短路线吗？
2. **可理解性：**作为授权工作的人，我是否理解产品决策、范围、主要风险和停止条件？
3. **技术正确性：**失败、取消、顺序、所有权、安全、上限和清理是否真正得到处理？

我有意不把这些视角合并成一个“全知 reviewer”。如果它们的建议冲突，或者合起来超过复杂度预算，任务就返回决策 Gate。我不会把每一条建议机械合并成一个更大的计划。

重点不是模拟委员会，而是避免一条推理链成为项目唯一能看见的现实。

## 测试是必要条件，证据才能关闭 Gate

最有用的一课来自一项不稳定的字幕测试。

测试假设一个 `Task.yield()` 足以让异步 stream 发布可观察状态。大多数时候确实如此。当统一项目 Gate 在不同计时条件下运行完整系统时，竞态暴露了出来。

错误做法是反复运行，直到它通过。正确做法是用对可观察状态的等待，替代对调度器行为的猜测。

这种区别后来塑造了整个工作流。绿色测试套件只能证明测试真正观察到的东西。它不能证明签名环境里的 Keychain 流程可以工作，不能证明 AVPlayer 可以在生成的流中 seek，不能证明 renderer 运行 30 分钟后释放了全部 layer，也不能证明窗口 resize 时 UI 仍然可用。

BiliKit 为静态检查、Package 测试和完整 App 构建提供同一个可复现入口。随后，高风险任务再追加自己真正需要的证据：

- 用 deterministic fixture 固定协议行为；
- 用负向测试覆盖来源和重定向策略；
- 用签名 smoke test 验证 Keychain；
- 用真实 AVPlayer probe 验证播放；
- 用受控高密度运行验证渲染；
- 用长时间测量验证内存和清理；
- 对自动化无法有意义判断的那一条产品路径，由用户人工确认。

一个里程碑不会因为代码存在就完成。只有代码、自动化 Gate、环境相关证据、当前文档和仓库状态彼此一致，它才真正完成。

这比接受“所有测试都通过”要慢，却比六个里程碑之后才发现测试证明了错误的东西快得多。

## Spike 必须被允许死亡

弹幕 renderer 又迫使我做出一次改变。

渲染大量移动文字层看起来像实现问题，但它首先是决策问题：哪条路线能够满足可读性和持续负载要求，同时不让渲染引擎比功能本身还大？

因此实验存在于明确不可合入的 spike 分支。它的任务是用合成负载比较少量候选，回答一个生产决策，而不是凭惯性长成可复用基础设施。

这在 AI 时代很重要，因为一次性代码不再显得昂贵。模型可以在几分钟内抛光 benchmark、加入配置、生成结果 schema，并让 harness 看起来足以进入生产。每项新增内容的低成本，会掩盖整个系统正在形成的总成本。

Spike 应该为学习和删除而优化。

结果选定路线后，生产工作从一份新契约重新开始。实验是证据，不是地基。它阻止了“意外架构”：临时代码因为已经能跑而存活下来，并在随后几年里定义产品。

## 我的工作向上移动，但没有消失

把这种变化描述为“从程序员变成架构师”很有诱惑力，但我不认为它完全准确。

我仍然阅读代码。我仍然需要充分理解 Swift 并发、所有权、AVFoundation、HTTP 行为、Keychain 语义和 Core Animation，才能拒绝那些看起来很像正确答案的胡话。AI 没有消除技术深度的必要性，它改变了技术深度最能产生价值的位置。

我花在输入常规实现上的时间更少，花在以下决策上的时间更多：

- 谁拥有一份状态；
- 哪一层被允许知道一个事实；
- 哪种失败代价高昂；
- 什么证据会改变下一步决定；
- 一个抽象什么时候才真正赢得存在权；
- reviewer 是在保护产品，还是在保护一个想象中的未来；
- 什么时候停止。

最后一点可能最重要。

AI 对继续生产没有天然阻力。再加一个 helper、一个 protocol、一层测试矩阵或一份文档，它都不会疲惫。传统开发内建了一种摩擦：编写代码昂贵，所以一些想法会在实现之前自然死亡。AI 辅助开发消除了这种摩擦，工作流就必须有意识地把判断重新放回系统。

人类不只是写 prompt 的人。人类是范围、风险和事实的 owner。

## 我现在使用的流程

当前循环已经和最初非常不同：

1. 阅读当前代码、roadmap、相关决策、测试和历史证据。
2. 定义一个可观察 Goal 和对应完成证据。
3. 按失败风险分类，而不是按预计行数分类。
4. 在探索不确定方案前设置复杂度预算。
5. 实现最小纵向切片。
6. 从独立只读上下文 review 有意义的修改。
7. 运行共享自动化 Gate。
8. 只追加该风险真正需要的真实环境证据。
9. 更新当前文档，但不重写历史。
10. 只有代码、证据、文档、CI 和 Git 状态一致时，才关闭里程碑。

这套工作流并非普遍最优。把它用在周末脚本上会非常荒谬。它之所以出现，是因为 BiliKit 已经大到、充满状态到、风险高到让“对话中的自信”失去价值。

令人意外的是，这种改变并不是 AI 不会写代码造成的，而是 AI 太会写代码造成的。

在同样时间里，若完全依靠自己，我很难在 V1 之前写出两万一千行。AI 让这个规模变得可达。随后，可达的规模暴露了一个依靠局部理解和非正式 review 的工作流中所有弱点。

代码变得廉价，一致性没有。

如果 AI 继续进步，我认为这种区别只会更重要。胜出的工作流不会是那个从模型中榨出最多代码的工作流，而是那个能够吸收生成代码，同时不失去所有权、边界、证据，以及说明系统实际行为能力的工作流。

BiliKit 仍然没有到版本 1。

但它已经改变了我构建软件的方式。我不再把 AI 对话当作工程事实所在的位置。对话是更大流程中的一个 worker。仓库保存记忆，契约保存意图，Gate 保存证据，独立上下文挑战故事。

而我仍然负责决定：什么时候，这一切才算足够好。
